Step by Step

02단계별 상세 설명

위 다이어그램의 6개 레이어를 데이터가 지나가는 순서대로 풀어서 설명합니다.

L1

소스 — 설비가 실시간으로 쏟아내는 6종 로그

상태조회·이벤트보고·주기수집·원격제어·알람보고·통신제어. 지금은 부서원이 시간 단위로 설비마다 개별적으로 찾아 쓰고 있는 원시 데이터입니다.

예: 주기수집 데이터의 상당수 필드는 ASML 암호화 스키마로 잠겨 있어 그대로는 활용 불가
L2

게이트웨이 — 암호화 해제와 표준 접근 창구

암호화 필드는 언락 파이프라인을 거치고, 6종 로그 전체는 MCP 게이트웨이를 통해 표준 인터페이스로 노출됩니다. 동시에 필드 의미는 현업 엔지니어가 검증하는 시맨틱 카탈로그에 누적됩니다.

이 계층부터 이미 타 파트 에이전트도 재사용 가능 — "우리만의 데이터"가 아니라 "사내 표준 접근 경로"
L3

시맨틱 융합 — 텍스트가 아닌 데이터를 LLM이 읽게 번역

시계열 인코더가 주기수집·상태 패턴을 벡터화하고, 지식그래프가 필드-공정-원인 관계를 연결하며, RAG가 과거 사례·매뉴얼에서 근거 문서를 찾습니다. 일반적인 "문서 임베딩 RAG"와 결정적으로 다른 지점입니다.

예: twin scan skew 패턴을 시계열 인코더가 벡터화 → 지식그래프에서 유사 과거 사례와 연결
L4

인지/판정 — 근거 기반 결론 + 실시간 1차 필터

LLM 판정엔진이 spec in/out과 원인 후보를 근거 로그와 함께 제시하고, 엔지니어가 등록한 도메인 로직은 Skill 레지스트리에 쌓입니다. 알람처럼 지연이 치명적인 경우 엣지 경량모델이 설비 근처에서 먼저 걸러냅니다.

엣지 모델은 A2A를 거치지 않고 알람보고 인터페이스로 직행하는 fast path를 가집니다(아래 다이어그램 점선 참고)
L5

A2A 오케스트레이션 — 파트 경계를 넘는 유일한 구간

판정 결과가 파트 내부에서 끝나지 않고, 표준 프로토콜로 스케줄링·MES·설비관리 에이전트에게 위임될 수 있습니다. 구체적인 구조와 해결하는 문제는 04 섹션에서 별도로 다룹니다.

다른 파트의 "우리 챗봇"과 근본적으로 갈라지는 지점
L6

인터페이스 — 엔지니어가 실제로 마주하는 화면

자연어 챗봇, 알람 자동보고, 대시보드, 주간 리포트 자동생성으로 결과가 도달합니다. 엔지니어 입장에서는 "물어보면 답이 오는" 경험이지만, 그 뒤에는 위의 5단계가 표준화되어 돌아갑니다.

Differentiation

03"우리도 MCP/RAG 한다"와 무엇이 다른가

한 문장 비교: 저들은 파트 안에서 문서를 검색하는 챗봇을 만들고, 우리는 파트 밖으로 데이터·판단을 연결하는 인프라를 만듭니다.

타 파트 · 일반적 MCP/RAG/Skill 스토어

📄텍스트 문서 임베딩 검색 중심
🏠파트 내부 챗봇 1개로 종료
🧩개발팀이 직접 라벨링 시도 (도메인 부족 리스크)
🔓이미 열려있는 datalake API 재활용
🤖LLM 1회 호출 + 단순 RAG
🎯지향점: "우리 파트의 AI 앱"
VS

본 플랫폼 · ASML 데이터 특화

⏱️ 시계열·이벤트·제어이력 등 이종 로그를 시맨틱 번역 후 융합
🔗 A2A로 파트 경계를 넘어 타 부서 에이전트와 협업
✅ 현업 엔지니어가 검증형 크라우드소싱으로 온톨로지를 채움
🔐 ASML 암호화 데이터 언락까지 포함한 게이트웨이 제공
⚡ 엣지 경량모델 + 클라우드 대형모델 하이브리드, 실시간성 확보
🏗️ 지향점: 사내 ASML 데이터/도구 표준 인프라
왜 데이터 형태 차이가 결정적인가 ▸
문서 임베딩 RAG는 수치 시계열의 "패턴"을 이해하지 못합니다. Twin scan skew처럼 여러 파라미터가 시간에 따라 함께 움직이는 현상은 텍스트 검색이 아니라 시계열 인코딩 + 지식그래프 기반 인과 추론이 필요합니다. 이건 아키텍처를 처음부터 다르게 설계해야 하는 문제이지, 같은 RAG 스택에 데이터만 바꿔 넣는다고 해결되지 않습니다.
왜 "범위" 차이가 조직적으로 중요한가 ▸
파트 내부에서 끝나는 챗봇은 그 파트의 생산성만 올립니다. 유휴시간·스케줄 조정처럼 실제 최대생산에 영향을 주는 결정은 대부분 파트 경계를 넘어야 발생합니다. A2A는 이 경계를 자동화된 요청-위임으로 없애는 유일한 장치입니다.
왜 도메인 지식 확보 방식이 다른가 ▸
우리 부서는 포토 공정 도메인 전문가가 아닙니다. 그래서 온톨로지를 직접 채우는 대신, 현업 엔지니어가 검증하고 등록하는 구조를 만들어 "모르는 데이터를 아는 사람이 채우는" 확장 가능한 구조로 설계했습니다.

Concept Deep-dive

04A2A는 실제로 어떻게 구성되고, 어떤 취약점을 해결하는가

A2A는 MCP·Skill·Agent를 대체하는 게 아니라, 이미 만든 세 가지 자산을 파트 경계 너머로 조립 가능하게 만드는 프로토콜 레이어입니다. 4단계로 작동합니다.

STEP 1

능력 공개 (Agent Card)

포토 에이전트가 "내가 할 수 있는 일"(예: 유휴 예측, spec 판정)을 표준 JSON 카드로 게시

STEP 2

탐색 & 매칭

스케줄링 에이전트가 "이 문제를 풀 수 있는 에이전트"를 카드 목록에서 검색·매칭

STEP 3

Task 위임

표준 메시지 포맷으로 작업을 위임 — 사전 협의된 API 없이도 동적으로 요청 가능

STEP 4

실행 & 승인 게이트

결과 반환 전, 리스크가 있는 조치는 사람 승인(HITL)을 거치고 모든 요청·응답이 로그로 남음

이 구조가 없다면 발생하는 취약점과, A2A가 이를 어떻게 해결하는지입니다.

🚫 취약점 1 · 파트 간 사일로

각 파트가 자기 에이전트만 만들어서, 서로 어떤 능력이 있는지 모른 채 같은 기능을 중복 개발함.

✅ Agent Card로 능력을 표준 공개 → 검색 가능해져 중복 개발 방지
🚫 취약점 2 · 수동 조율 지연

설비 유휴가 예측돼도, 사람이 메신저·전화로 타 부서에 요청해야 스케줄이 조정됨 — 대응이 항상 늦음.

✅ 표준 Task 위임으로 에이전트 간 즉시 요청 → 유휴시간 대응 지연 최소화
🚫 취약점 3 · 책임 추적 불가

누가 언제 무슨 근거로 어떤 조정을 요청했는지 기록이 남지 않아, 문제 발생 시 원인 추적이 어려움.

✅ 모든 요청·응답이 로그화되어 감사 추적(audit trail) 가능 — 거버넌스 확보

Raw Material

05부서원이 원하는 6종 설비 로그

현재 시간 단위로 설비마다 개별적으로 찾아 쓰고 있는 6가지 로그 유형을, 하나의 표준 파이프라인(01 다이어그램의 L1)으로 묶습니다.

① 상태조회

설비 현재 가동/대기/이상 스냅샷. 실시간 헬스체크·대시보드 기초 데이터.

② 이벤트보고

공정 진행 중 발생 이벤트 로그. 원인분석·ID Dump의 핵심 입력.

③ 주기수집

일정 주기로 쌓이는 파라미터 시계열. Focal Curve·Final XY 판정의 원천.

④ 원격제어

엔지니어/시스템이 설비에 내린 제어 명령 이력.

⑤ 알람보고

이상 발생 시 즉시 발생. 가장 시급한 자동 1차 분석 대상.

⑥ 통신제어

설비-시스템 간 통신 상태/오류. 원격제어 반영 여부 검증 근거.

Use Cases

06대표 유즈케이스

UC1 · 알람 대응 자동화

알람 발생 → 원인 후보 자동 제시

알람보고→이벤트보고 대조→과거 유사사례 RAG 검색→원인 후보 + 근거 인용
엔지니어의 로그 탐색 시간을 없애 알람 대응(MTTR) 단축에 기여.
UC2 · 자연어 상태 리포트

"이번 주 A라인 상태 요약해줘"

상태조회+주기수집→시계열 패턴 요약→자연어 리포트
수작업 취합을 자동화해 보고 준비 시간 절감.
UC3 · 제어 명령 검증

원격제어가 의도대로 반영됐는가

원격제어 로그→통신제어 대조→불일치 즉시 알림
제어 실패의 뒤늦은 발견을 줄여 rework·품질 리스크 감소.
UC4 · Spec 판정 자동화

Focal Curve / Final XY 자동 in·out 판정

주기수집 실측치+spec→LLM 판정→근거 인용 결론
반복 판정 업무를 줄이고 판정 일관성 확보.
UC5 · A2A 파트간 협업 (핵심 차별 유즈케이스)

"이 설비 곧 유휴 예상 — 스케줄링 조정 검토해줘"

포토 에이전트: 유휴 예측→A2A Task 위임→스케줄링/MES 에이전트: 대안 검토→사람 승인 후 반영
사람이 부서 간 연락하던 조율을 에이전트 협업으로 대체 — 유휴시간 최소화에 직접 기여.
